# 项目开发状态评估（2026-10-13）

本次根据当前代码、需求及完成矩阵、本地实际测试和 GitHub Actions 记录进行评估。目的是说明开发阶段、未完成部分及下一步，不把历史文档中的勾选或流水线总状态直接当作上线证据。

## 1. 总体判断

项目处于**主要业务已实现、仍需补齐部分业务规则和预发验收的阶段**。用户 Web、商户 Web、管理 Web、Flutter 和后端都有实际业务实现，已经具备较完整的 MVP 基础；目前不能判定为可正式上线。

- M1–M5：浏览、账号、点评、搜索、交易预订、商户经营和后台治理的主要流程已落地。
- M6–M7：Flutter 和社区主要流程已落地，地图、推送、支付等仍需要真实环境与真机验证。
- 后续增长运营：已有不少页面和接口，但秒杀拼团、创作者奖励、实验分组等仍属于基础实现，不能全部按成熟业务闭环计算。
- 发布：脚本和工作流已经存在，但当前核验到的发布记录没有实际执行部署。

不提供“完成 90%”之类百分比：需求清单同时包含首发、延期和远期功能，没有统一工作量分母。按业务阶段和验收证据判断更可靠。

| 项目 | 当前证据 | 下一步 |

| 秒杀/拼团未接入交易履约 | [MarketingCampaignService](../backend/src/main/java/com/tuowei/dazhongdianping/module/marketing/service/MarketingCampaignService.java) 只做参与记录、扣活动名额、开团/参团；普通下单参数只有 `dealId/quantity/userCouponId`，没有活动或团单关联。Web/App 页面也停留在领取编号和组队结果 | 若首发开放这两项，应补活动价订单、支付、成团履约、超时失败及退款/库存释放；否则明确延期 |

| 多支付渠道仍缺实现 | [PaymentChannelResolver](../backend/src/main/java/com/tuowei/dazhongdianping/module/trade/payment/PaymentChannelResolver.java) 只有 Stripe 与 mock；[StripePaymentChannel](../backend/src/main/java/com/tuowei/dazhongdianping/module/trade/payment/StripePaymentChannel.java) 指定 `card`；PayPal 只有配置字段 | PayPal、真实支付宝/微信、SEPA/iDEAL/Klarna 需实际适配；Apple Pay/Google Pay 也不能因引入 Stripe SDK 就视为已完成 |
| 第三方内容审核缺适配器 | 实际提供者是 [KeywordContentModerationProvider](../backend/src/main/java/com/tuowei/dazhongdianping/module/moderation/service/KeywordContentModerationProvider.java)，基于敏感词匹配 | 当前可以敏感词与人审起步；若引入外部图文机审，需要实现供应商调用、结果映射与故障策略，不能仅填密钥 |
| 双语点评是社区人工译文 | [ReviewTranslationService](../backend/src/main/java/com/tuowei/dazhongdianping/module/review/service/ReviewTranslationService.java) 保存用户提交的 zh/en 译文，Web/App 均有入口 | 自动翻译属于另一个尚未实现的能力；若需要，再补翻译服务、缓存及译文治理 |
| 实验开关是基础版 | [ExperimentService](../backend/src/main/java/com/tuowei/dazhongdianping/module/experiment/service/ExperimentService.java) 的匿名开关仅按 `flagKey` 哈希，同一开关对所有用户结果一致；实验分组由调用方提交 A/B | 真正按用户百分比灰度、服务端稳定分流、曝光转化统计仍需建设 |
| 发票是申请与登记流程 | [AdminInvoiceService.issue](../backend/src/main/java/com/tuowei/dazhongdianping/module/invoice/service/AdminInvoiceService.java) 接受管理员填写的发票号并更新状态 | 若需自动生成/交付正式税务票据，应另接开票与交付服务，不能把登记流程当作自动税务系统 |

还有两个应按规模决定的后续项：PC 已有静态/真实数据快照预渲染，常驻 SSR 尚未实现；通用 [InProcessMessagePublisher](../backend/src/main/java/com/tuowei/dazhongdianping/module/messaging/service/InProcessMessagePublisher.java) 写 outbox 后直接标记已发布，不是外部消息队列的可靠投递系统。现阶段不必为了架构齐全立即引入复杂基础设施。

PC 社区只读、PC 不做地图、私信不做群聊/语音以及视频点评延期，均属于既定范围选择，不应误报为开发遗漏。

## 6. 建议下一步顺序

| 顺序 | 工作包 | 完成标准 |
| --- | --- | --- |
| P0-1 | 收尾当前版本、恢复可靠回归 | 定位权限 E2E 超时；审阅现有 SLA 未提交修改；候选提交通过完整 CI、nightly，以及 21–24 号新增 MySQL 迁移验证；以同一不可变 SHA 记录结果 |
| P0-2 | 明确 EU 首发实际开放范围 | 定首发城市、币种、门店时区及开放菜单；创作者奖励、秒杀拼团若开放就补业务规则，否则明确延期；已有预发基线允许地图、推送和正式商店发布延期 |
| P0-3 | 打通一次真实预发业务与发布 | 按环境清单配置；用户真实收验证码 → 下单 → Stripe 付款 → 发券 → 商户核销/退款 → 平台对账；再完成部署 smoke、备份及回滚演练 |
| P1 | 补齐保留在产品范围内的深度功能 | 营销交易履约、任务成果核验、GBP/多时区、多支付渠道、真机地图推送、正式移动发布，分别建立验收用例 |
| P2 | 依据实际流量与运营需要增强 | 自动翻译、第三方机审、用户灰度实验、持续 SSR、外部消息队列、算法推荐等 |

最值得立即投入的工作是 **P0-1：让当前版本成为能稳定回归、可追溯的发布候选**；随后用真实 EU 预发完成业务与部署验收。继续增加页面数量，不会自动解决目前的上线缺口。
