# AWS EU test Terraform baseline

This root module describes the paid AWS infrastructure needed by the repository's
EU `test` release path. It is fixed to Paris (`eu-west-3`) and does not create
anything until an operator explicitly runs `terraform apply` with an approved AWS
identity. Repository development and CI must stop at formatting, validation, and
plan review unless paid-resource creation has been separately approved.

## Scope

The module declares:

- one VPC across two availability zones, with two public and two private data
  subnets;
- one Ubuntu 24.04 EC2 target with an Elastic IP, IMDSv2, encrypted root volume,
  and an instance role used by the AWS default credential chain;
- private RDS MySQL with `require_secure_transport=1` and an RDS-managed master
  password in Secrets Manager;
- private single-node ElastiCache Redis with transport/at-rest encryption and a
  generated password stored in Secrets Manager;
- private single-node OpenSearch with HTTPS, node/volume encryption, fine-grained
  access control, and generated internal-user credentials in Secrets Manager;
- a private, encrypted, versioned S3 asset bucket exposed for reads only through
  a SigV4 CloudFront origin access control; and
- security groups that expose only SSH from reviewed CIDRs and nginx ports 80/443,
  while MySQL, Redis, and OpenSearch accept traffic only from the EC2 target group.

The OpenSearch resource policy permits HTTP actions for any principal because the
application authenticates with the internal user database rather than SigV4. The
domain is inside the VPC and its security group admits port 443 only from the target
host, so this policy does not make the domain publicly reachable.

This module intentionally does **not** create DNS records, trusted nginx
certificates, an application database user, the private runtime env/MySQL client
files, SMTP/Twilio/Stripe accounts, GitHub Environment values, backups outside the
declared service defaults, or deployment evidence. Those remain explicit
provisioning and acceptance steps.

## Identity boundary

The Canonical AMI's `ubuntu` account is the privileged provisioning identity.
Cloud-init also creates `deploy` with the reviewed SSH public key but gives it no
general sudo permission.

1. Run Ansible as `ubuntu`; the playbook uses `become` to install packages,
   systemd/nginx configuration, and the repository's exact sudoers policy.
2. Configure GitHub Releases to SSH as `deploy`; that account can only restart,
   stop, and inspect the four named application services through the installed
   minimal sudoers rules.

Do not add `deploy` to the sudo group or use it as the Ansible provisioning user.

## Validate without AWS access

From this directory:

```bash
terraform fmt -check -recursive
terraform init -backend=false
terraform validate
```

`init -backend=false` downloads provider schemas but neither configures remote
state nor contacts AWS APIs. `validate` does not prove that quotas, instance types,
engine versions, names, or account policies will accept the configuration.

## Prepare a reviewed plan

Copy the two examples to ignored working files and replace every placeholder:

```bash
cp terraform.tfvars.example terraform.tfvars
cp backend.hcl.example backend.hcl
terraform init -reconfigure -backend-config=backend.hcl
terraform plan -out=aws-eu-test.tfplan
terraform show aws-eu-test.tfplan
```

The S3 state bucket and DynamoDB lock table must already exist, have encryption and
versioning enabled, and use restricted operator/CI policies. Redis and OpenSearch
passwords are generated by Terraform and therefore exist in encrypted state even
though outputs expose only secret ARNs. Never commit `backend.hcl`, `terraform.tfvars`,
plan files, state, private keys, or retrieved secret values.

Before any apply, review at least:

- the AWS account/role and `eu-west-3` region;
- monthly cost and cleanup ownership for EC2/EIP, RDS, ElastiCache, OpenSearch,
  CloudFront, S3, logs, snapshots, data transfer, and Secrets Manager;
- the non-public SSH CIDRs, DNS/TLS plan, service quotas, backup/restore plan, and
  destroy behavior (`database_skip_final_snapshot` defaults to `true` for the
  disposable test baseline); and
- whether an OpenSearch service-linked role already exists and must be imported
  rather than created by this state.

Do not run `terraform apply` merely because validation or plan succeeds. Paid
resource creation requires explicit approval of the reviewed plan.

## After an approved apply

Terraform outputs only non-secret endpoints and secret ARNs. Retrieve the actual
values through an approved Secrets Manager channel, create a dedicated application
and migration database identity instead of leaving the service on the RDS master
account, and build `eu-test.env` plus `mysql-release.cnf` outside Git.

Then update the ignored Ansible inventory with the EIP and keep
`ansible_user: ubuntu`:

```bash
ansible-playbook \
  -i ../../ansible/inventory.yml \
  ../../ansible/provision-target-host.yml \
  -e @../../ansible/vars/test.yml \
  --syntax-check
```

Only after provisioning, DNS/TLS installation, private runtime configuration, and
the repository's target-host preflight succeed should GitHub Environment use
`DEPLOY_SSH_USER=deploy`. The EC2 instance role supplies S3 credentials through
`APP_S3_CREDENTIALS_PROVIDER=default_chain`; do not install long-lived AWS access
keys on the target.
